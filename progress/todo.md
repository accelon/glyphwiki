# P0-1　把去內嵌批次接進字庫，然後拿掉 v3 的 comp 區段

### 要做什么

把 `tools/deinline-batch.ts` 產生的異體部件**寫進字庫**：

1. 每個新異體成為一個真的字形，掛在它對應部件碼位的家族底下；
2. 來源字裡那組原始筆劃換成一個引用（恆等框）；
3. 完成後把 v3 尾端的 **IDS 部件區段整段拿掉**，字庫降回 v2。
   此後 IDS 就**完全不出貨**，只留在建置期的 DB 裡當鷹架。

### 為什麼

這是師父最早要求的「把 GlyphWiki 和 IDS 合起來」的正解。目前的做法是
**把 IDS 直接塞進出貨的字庫**（v3 的 `comp` 區段），那等於讓「內部開發輔助資訊」
變成消費者要讀的資料——分層錯了。正確的分層是：

* IDS ＝ **建置期**用來判斷「這批筆劃屬於哪個部件」的依據，用完就拆；
* 字形繪製資料 ＝ 使用者唯一接觸到的東西，部件關係必須**長在繪製資料上**。

做完之後，`杏`（U+674F）之所以找得到「木」，是因為它真的引用了木，
而不是因為旁邊附了一張 IDS 對照表。

### 已經有的東西

* **批次產生器**：`tools/deinline-batch.ts`（320 行）——分組、造異體、渲染比對、寫 TSV。
* **獨立驗證器**：`tools/verify-deinline.ts`（171 行）——讀 TSV、逐字重建、逐像素比對。
  兩支工具**互相對帳**，先前就是靠這一點抓出「只修代表字形」的 bug。
* **產物**：`out/deinline-variants.tsv`（315.7 KB）。
  欄位：`name, source_cp, source_name, comp_cp, comp_name, group, k, at, slots, n_strokes, data`。

### 核心做法（這招是關鍵，別退回舊路）

**不要去家族裡找「形狀接近」的現成異體。** 那條路走不通：KAGE 的引用框是
**非等比映射**，硬套會壓到筆寬，實測最佳只有 IoU 70.3%（`u6728-03` 對 `杏` 的木）。

改成：

1. 把那組原始筆劃**原封不動**做成一個新異體字形（座標一個都不動）；
2. 用**恆等框** `[0,0,200,200]` 引用它。

渲染路徑走的是同一批座標，所以**逐像素相同**。全批 IoU 100.00%，兩支獨立工具
都驗過、0 例外。也就是說：**我們把前人嫌麻煩沒做的那些異體補做出來了。**

### 命名

`inl-<來源碼位>-<序號>`，例如 `inl-674f-0`。不沿用 GlyphWiki 命名慣例
（沒有要回報上游，而且有撞名風險）。TSV 裡的 `source_cp`／`source_name`
就是「這個異體是從哪個字來的」的記錄。

### 目前規模（**已對現行字庫重跑**）

> 這一節原本是警告「TSV 已經過期」。**該檔案已經重新產生**（`bun run tools/deinline-batch.ts`），
> 下面的「重跑」欄就是現在的內容，兩支工具互相對帳、0 例外。施工時直接用它即可。

| | 已提交的 `out/deinline-variants.tsv` | 對**現行**字庫重跑 |
| --- | ---: | ---: |
| 還原成功的字 | 1,401 | **1,356** |
| 產生的異體部件 | 1,831 | **1,771** |
| 分組 `+` / `/` / `@` | 463 / 1,153 / 215 | 445 / 1,117 / 209 |
| 涉及部件種數 | 560 | — |
| 渲染比對 | 100.00% | 100.00% |

**兩者為什麼不一樣**：P2-4 的 IDC 修正（`build-library.ts` 只讓落在字集區段內的
碼位有家族）讓 U+2FF0–U+2FFB 不再算字。IDS 分量裡如果出現組字運算子，
`indexOfCodePoint` 現在回 `undefined`，那顆字就歸到「部件不在庫中」而跳過——
該類從 253 筆增加到 **344 筆**，代價是少修 45 個字。

這件事本身是對的（先前那 45 個字是在**對 ⿰ 造異體**），但它意味著：

> **接進字庫之前要先重跑批次**，用現行的字庫、產生新的 TSV，不要拿舊的那份施工。
>
> ```
> bun run tools/deinline-batch.ts --out out/deinline-variants.tsv   # 重建（會覆蓋）
> bun run tools/verify-deinline.ts                                  # 獨立再驗一次
> ```

### 怎麼接進字庫（建議路徑）

`build-library.ts` 目前的資料流是：讀 DB 的 `glyphs`／`parts` → 建家族 →
寫二進位。要接進去有兩種切法，**要先確認哪一種**：

* **(A) 做成 DB 的預處理步驟**（建議）——新增 `tools/apply-deinline.ts`，
  讀 TSV，把新異體寫成 `glyphs` 的額外資料列、把來源字的 `parts` 改成引用。
  之後 `build-library.ts` 一行都不用改。好處是修補變成**可檢視的 SQL 資料列**，
  也可以重跑。
* **(B) 做成 `build-library.ts` 的一個旗標**——在記憶體裡改，不落地。
  好處是不動 DB，壞處是每次建字庫都要重算。

不論走哪條，**每一步都要留 IoU 100% 的驗收閘門**：任何一個字低於門檻就整顆不改。
寧可少做，也不要默默畫壞。

### 風險

1. **這些異體是上游沒有的新字形。** 它們是規則衍生的（可重新產生），
   但字庫從此與上游 GlyphWiki 分岔，而且分岔會逐年擴大。這是已經拍板的方向
   （「我們一定會和 GlyphWiki 慢慢脫鉤」），但要清楚記在文件裡。
2. **家族表會變動**：新成員要插進家族、`pref`／`plain` 會位移。
   動完務必重跑 `check-lib-compat.ts`（它會驗 `pref <= 31`、`plain <= 7`、
   成員連續、`orphanStart` 一致）。
3. **拿掉 comp 區段是破壞性變更。** 要確認所有消費者都改走
   `lib-format.ts` 的 `componentKids(L, gi)` 之後才移除。
   已確認在用的有：`build-glyph-browser.ts`（已改用 `LIB.comp`）、
   `free-compose.ts` 的 `searchByComponent`（已接上，IDS-only 命中標
   `idsOnly: true`）。**要先確認**還有沒有別的地方直接讀 `lib.comp`。
4. **`slots` 欄位不能簡化成「起點＋長度」。** 原始 `strokes` 陣列裡
   引用與原始筆劃是**交錯**的，用連續區間會搬到錯的筆劃——
   `verify-deinline.ts` 一開始就是這樣跟批次對不上，靠 `slots` 才對齊。

### 工作量

約 **1 個工作天**：接線 0.5 天、全庫驗收與五支測試 0.5 天。批次本身已經跑得動，
不用重寫。

# P1-2　合併重複的家族成員

### 要做什么

把家族裡**畫出來完全一樣**的成員從字庫合併掉。

### 為什麼

同一個碼位底下掛著好幾個渲染結果一模一樣的成員，只會讓「異體」清單變長、
看不出差異。使用者已經反映過：「幾乎所有的字，開頭兩個異體都是一樣的，
如 U+4E23」。

已經查清楚的兩種：

| 類型 | 說明 | 規模 |
| --- | --- | ---: |
| **純指標** | `uXXXX` 整個字形只有**一個** `99` 引用，指向同家族的 `uXXXX-j`——它是別名，不是另一個字形 | 丣 U+4E23 就是（`u4e23` 1 筆、`u4e23-j` 9 筆） |
| **資料一字不差** | 筆劃座標完全相同 | **4,969 個家族、6,455 個多餘成員** |

（第二列的數字來自 `tools/family-dup.ts`，但那是在 **IDC 修正之前**量的，
要重跑才是現值。）

### 已經做了什麼

**只有 UI 層**：`tools/glyph-browser-page.js` 的 `dedupeFamily()`
會濾掉純指標與資料相同的成員，並在面板上註明「已濾掉 N 個畫出來一樣的」。
**字庫本身還沒合併**。

### 怎麼做

1. 先寫一支**只報告不動手**的掃描（`family-dup.ts` 已經有一半），
   列出「將被移除的成員」與「留下來的代表」，輸出成 TSV 供人工抽查。
2. 合併規則建議：純指標一律移除（保留本體）；資料相同者保留 `pref` 指到的那個。
3. 動到 DB 或建置流程，重跑五支驗收。

### 風險

* **會動到 `pref`／`plain` 與成員索引**，而 `indexOfCodePoint` 的代表字形
  就是從這裡選的。合併後同一個碼位的代表字形可能換人——**要逐一比對
  「合併前後 `indexOfCodePoint(cp)` 指到的是不是同一個字形」**，
  不一樣的要人工看。
* 純指標成員有時是**別的家族的引用目標**（有人引用 `u4e23` 而不是 `u4e23-j`）。
  移除前要確認沒有懸空引用（`build-library.ts` 已經會擋，但會在報告裡多出
  「懸空引用」警告）。

### 工作量

**0.5–1 天**。掃描與報告半天；實際合併加上驗收半天。建議**先只做純指標那一類**
（低風險、數量少、立刻看得出效果），資料相同的那 6,455 個留到之後。

# P2-4　加收 CJK 部首（2E80–2EFF）與康熙部首（2F00–2FDF）

### 要做什么

把這兩個區段加進字庫的收錄範圍，讓部首形（⺊、⺡、⺮…）也有真的字形可以引用。

### 為什麼

去內嵌批次有一類跳過是**「部件不在庫中」**——目前 **344 筆**。
被跳過的原因很單純：那些 IDS 分量的碼位落在部首區，而字庫只收
12 個 CJK 漢字區塊。不收就沒有字形可以引用，也就沒辦法把筆劃還原成部件。

### 怎麼做

`build-library.ts` 已經有 `--ranges`（第 98–113 行），檔案開頭的用法註解甚至
就寫著：

```
bun run tools/build-library.ts --ranges 4E00-9FFF 2FF0-2FFB   # 順便收組字運算子
```

看起來只是改 `DEFAULT_RANGES` 就好。**但沒有這麼單純，見下面。**

### ⚠ 風險：這跟 IDC 的教訓直接衝突，要先想清楚

剛修掉的 IDC bug 是：GlyphWiki 把 IDS 合成字形命名成 `u2ff0-u9b2f-u5bf8`，
dump 也把它標成「⿰ 的異體」，於是 ⿰ 底下掛了 698 個成員、⿱ 掛了 2,270 個
（全庫 77,353 個 `u2ff?-*` 名字），「某個異體被誰引用」就會撈出 U+2FF0
這種根本不該出現的 IDC。修法是**只讓落在字集區段內的碼位有家族**。

於是問題來了：**「加區段」就等於「承認那個碼位是字」。**

| 把 2E80–2FDF 加進 ranges 之後 | 後果 |
| --- | --- |
| 部首碼位有家族、有代表字形 | ✓ 可以當部件被引用 |
| 部首碼位會出現在**預設瀏覽清單**裡 | ？ 使用者想在字集瀏覽頁看到 ⺊ ⺡ ⺮ 嗎 |
| 部首碼位會出現在**搜尋結果**裡 | ？ 搜「木」會不會撈出一堆部首形 |
| 如果 2FF0 也被加進去 | ✗ 77,353 個合成字全部復活，IDC bug 原樣重現 |

**建議先把兩個概念分開**（這也是 P0-1 的精神）：

* **「碼位是字」**（有家族、有代表字形、進瀏覽清單與搜尋結果）；
* **「碼位可以當部件」**（有字形、可以被引用、`indexOfCodePoint` 找得到）。

`lib-format.ts` 的家族表目前把兩者綁在一起。要嘛：
(a) 部首只當部件、不當字（需要新的「部件字形」概念，`orphanStart` 那一段
本來就放這種東西，可能要擴充）；或
(b) 部首也當字，但排除在預設清單與搜尋之外（在 UI 層過濾，字庫不管）。

**要先確認哪一種，以及 `out/lib-cjk-all.ids` 這條線有沒有別的假設。**

# P2-5　去內嵌批次跳過的「筆劃數對不上」

### 要做什么

調查那一類跳過，看有多少是「其實做得到、只是我的分組沒模型化」。

### 為什麼

目前是最大的一類跳過：**1,240 筆**（session 末最後一次執行是 1,280）。
批次的閘門是「每個部件的預期筆劃數加總必須等於該字自己畫的筆劃數」，
對不上就整顆不改。這個閘門本身是對的（分錯組渲染看不出來，但會污染檢字），
但「對不上」有很多種原因，不能一概而論。

### 怎麼做（先調查，不要先寫程式）

**先做一次分類統計**：把 1,240 筆按落差分成幾類（差多少、差在哪個部件、
部件的筆劃數是幾畫），輸出成報告再決定。我的**猜測**（尚未驗證，要確認）是：

1. **部分部件已是引用、部分被拆**——`covered` 的算法用「引用可達」扣掉已涵蓋的
   部件，但如果一個部件被拆成「一半引用一半筆劃」，兩邊都對不上；
2. **部件本身在 GlyphWiki 也是拆的**——那個部件的字形不是原子，筆劃數算出來
   比 IDS 預期多；
3. **IDS 的分量數與 KAGE 的實際引用數不一致**（例如 IDS 說兩個分量、
   KAGE 引用了一個又畫了另一個）。

第 1 類值得做，第 2、3 類可能不值得。

### 風險

* **不要為了降低跳過數而放寬閘門。** 那個閘門是目前唯一的語意正確性防線
  （IoU 只驗渲染，驗不出分組對錯）。
* 如果決定放寬，要改成「允許指定容差 ＋ 記錄」，而不是拿掉。

### 工作量

**先調查 0.5 天**（寫一支分類統計的探針）。實際修法要等調查結果才知道，
可能 0.5–2 天。

# P2-6　去內嵌批次跳過的 `@` 多部件

### 要做什么

處理「佈局不是單純上下左右、而且內嵌部件多於一個」的情況（**349 筆**）。

### 為什麼

批次的分組方式只有三種：`+`（⿰⿲ 按 x 切）、`/`（⿱⿳ 按 y 切）、
`@`（其餘全部）。`@` 目前**只要內嵌部件多於一個就整顆跳過**——
因為切不出來就不知道哪幾筆屬於哪個部件。

這一類就是師父說的「嵌套、包圍」：⿴⿵⿶⿷⿸⿹⿺⿻ 這些算子。

### 怎麼做（先調查）

師父的方向是「數量不多，就加設一個符號 `@`」——`@` 已經在了，缺的是
`@` 底下的實際切法。**要先看那 349 筆到底長什麼樣**：

1. 列出這 349 筆的 IDS 算子分佈（哪些算子最多）；
2. 對每一筆印出「筆劃數對帳」的結果（哪個部件差幾筆）；
3. 再判斷有沒有通用的切法。

包圍結構（⿴⿵⿶⿷⿸⿹⿺）通常有一個「外框部件」與一個「內容部件」，
筆劃數對帳可能就足以二分；⿻（重疊）最難，可能永遠做不了。

### 風險

* 嵌套／包圍的**空間切法容易切錯**，而切錯的渲染是對的（因為筆劃只是搬到
  子字形再引用回來），只有**部件歸屬**會錯。所以照樣需要筆劃數對帳當閘門。
* 349 筆只佔 2,230 筆的一小部分，**投報率要自己判斷**。

### 工作量

**先調查 0.5 天**；實作 0.5–1.5 天，取決於算子分佈。

# P3-7　異體反查只做直接引用

### 要做什么

「按異體查字」目前只找**直接引用**那個字形的字。要不要再做一層
「深層反查」（用了引用 `木-01` 的那個部件的字）？

### 為什麼

`glyph-browser-page.js` 的 `runVariantSearch()` 用 `REFBY`（反向引用索引，
字形索引 → 直接引用它的父字）。所以：

* 「用了寫成 `木-01` 的那個木」→ 找得到；
* 「用了引用 `木-01` 的那個部件的字」→ **找不到**。

### 怎麼做

再建一份深層反向索引（成本與 `DEEP` 同級：29 萬筆引用走一遍）。
或者查詢時即時展開（慢）。

### 風險

* 記憶體：`DEEP` 已經是「碼位 → 父字」的全展開，再加一份會多佔幾 MB。
* **要先確認**這是不是真的需要——直接引用多半就夠用了。

### 工作量

**0.5 天**。

**一個值得記下來的工程教訓**

`tools/glyph-browser-page.js` 之所以被抽成獨立檔案，是因為頁面程式碼寫在
builder 的樣板字串裡會踩**兩個方向**的跳脫問題：

1. **寫的時候**：`\"` 會被吃掉、反引號會提前結束字串（同一個坑踩過三次，
   每次整頁空白）。
2. **抽出來的時候**：為了樣板字串寫的 `\\+`、`\\s`、`\\uFE35` 會**原封不動留著**，
   語意整個跑掉。實際症狀：`parseCpInput("U+908F")` 的 regex 變成 `/u\\+/`
   對不上，掉到 fallback 回傳 `'U'` 的碼位 **85**，「跳到碼位」全部失效。

**頁面程式碼不要再搬回樣板字串。** builder 也因此從 48 KB 降到 12 KB。
